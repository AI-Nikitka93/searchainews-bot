## 🔥 BOTTLENECKS
1. `PRF-001` `MEASURED` `High` — tail latency резко растёт уже на лёгком burst: `/health p95 592.5ms / p99 1064.6ms`, debug webhook `p95 529.2ms`.
2. `PRF-002` `ESTIMATED` `High` — scoring backlog pressure: локально видно `533 pending` против `54 scored`; при текущей cadence (`ai_analyzer.py --limit 40` hourly в GitHub Actions и `analyzePendingItems(env, 5)` hourly в Worker cron) теоретический drain без новых входов около `11.8h`, а новые items продолжают приходить.
3. `PRF-003` `ESTIMATED` `Medium` — anti-burst layer слабый: Worker rate limit держится на локальном `Map`, а при `buckets.size > 5000` просто делает `clear()`, что плохо масштабируется и не синхронизируется между isolates.
4. `PRF-004` `ESTIMATED` `Medium` — retry logic в delivery path использует fixed backoff без jitter, что повышает риск synchronized retry spikes при `429/5xx`.

## ⚠️ RELIABILITY RISKS

## Perf Summary
- **Perf status:** сильный baseline на одиночных запросах, но слабее ожидаемого under burst и с ограниченной visibility в проде.
- **Главная измеренная проблема:** live Worker paths теряют tail latency под умеренной конкурентной нагрузкой без роста error rate.
- **Главный reliability-риск:** backlog и delivery path опираются на cadence/retry модель, которая выглядит рабочей, но без distributed throttling и без полноценных telemetry signals.
- **Главный следующий шаг:** снять real k6-style thresholded test на `webhook/debug/health`, затем укрепить rate-limit/retry path и backlog drainage.

## 🛠️ TOP FIXES
1. Вынести perf smoke в воспроизводимый load script с thresholds (`p95`, `p99`, `http_req_failed`) и гонять его перед релизными изменениями Worker.
2. Усилить anti-burst слой: заменить in-memory limiter на более устойчивую стратегию для multi-isolate deployment или как минимум убрать `clear-all` поведение и добавить bounded eviction.
3. Добавить jitter к retry/backoff в Telegram delivery path, чтобы `429/5xx` не создавали синхронных повторов.
4. Поднять минимальный observability baseline: latency histograms, error counters, request correlation, отдельные сигналы по queue/backlog.
5. Свести scoring cadence и backlog reality: либо увеличить throughput анализа, либо урезать feed pressure, иначе freshness будет деградировать даже без явных падений.
